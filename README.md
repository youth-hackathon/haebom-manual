# 해봄 매뉴얼 서버

자주 하는 요청을 **매뉴얼**로 만들어 두고, 그 요청이 오면 모델을 부르지 않고 바로 안내하는 서버입니다. 매뉴얼에 없는 요청과 매뉴얼이 모르는 화면은 artemis 서버(baseline)에 그대로 넘깁니다.

매뉴얼은 사람이 손으로 쓰지 않습니다. 저작 서버가 에뮬레이터에서 요청을 실제로 따라 해 보면서 규칙을 만들고, 같은 요청을 규칙만으로 다시 따라가 봐서 끝까지 가는 것만 내보냅니다.

2026 서울AI디지털배움터 청년AI해커톤, 팀 Toolus의 저장소 가운데 하나입니다.

```
 해봄 앱 ──화면 상태──▶ 앞단 서버 ──맞는 규칙이 있으면──▶ 바로 답함 (모델 0번)
         ◀──동작 하나──     │
                            └──없으면──▶ artemis 서버 (baseline) ──▶ 모델

 저작 서버 ──adb──▶ 에뮬레이터 (해봄 앱 + 사람 역할)
     │
     └── manuals/*.json ──▶ 앞단 서버가 읽음
```

| 저장소 | 하는 일 |
|---|---|
| [haebom-app](https://github.com/youth-hackathon/haebom-app) | 화면 위에 다음에 누를 곳을 안내하는 Android 앱 |
| [haebom-artemis](https://github.com/youth-hackathon/haebom-artemis) | 화면 상태를 받아 다음 동작 하나를 고르는 서버 |
| [haebom-tts](https://github.com/youth-hackathon/haebom-tts) | 안내 문장을 소리로 바꾸는 서버 |
| haebom-manual (여기) | 매뉴얼을 만드는 저작 서버와, 매뉴얼로 먼저 답하는 앞단 서버 |

다른 저장소는 고치지 않습니다. 앞단 서버는 artemis 서버와 같은 요청을 받고 같은 응답을 돌려주므로([`docs/interface.md`](docs/interface.md)), 앱은 안내 서버 주소만 이쪽으로 바꾸면 됩니다. artemis 서버는 앞에 무엇이 있는지 모릅니다.

## 매뉴얼

매뉴얼 하나는 JSON 파일 하나이고([`manuals/`](manuals/)), 맡는 요청 문장과 규칙 목록입니다. 규칙 하나는 "이 화면이면 이 동작"입니다.

```json
{
  "instruction": "블루투스 화면으로 이동하기 위해 연결된 기기를 누릅니다.",
  "screen_condition": {"all": [{"foreground": "com.android.settings"},
                               {"node": {"text": "연결된 기기"}},
                               {"node": {"text": "설정 검색"}},
                               {"node": {"text": "서비스 및 환경설정"}}]},
  "done_condition": {"name": "click", "target": {"text": "연결된 기기"}}
}
```

- **화면 조건**은 화면에 보이는 것으로만 만듭니다: 앞에 있는 앱(`foreground`), 화면에 있는 요소(`node`: 글자 `text`, 설명 `desc`, id, 스위치의 켜짐 `checked`), 그리고 이들을 묶는 `all`, `any`, `not`. 좌표는 조건에 없습니다.
- **동작**은 artemis의 동작 그대로이고, 대상은 좌표가 아니라 이름으로 적습니다. 좌표는 요청이 올 때마다 그때의 화면에서 다시 찾습니다. 그래서 목록이 조금 밀려 있어도 맞습니다.
- 조건이 맞는 규칙이 여럿이면 **가장 뒤의 것**을 고릅니다. 그래서 이미 지나간 단계는 건너뛰고, 중간에서 시작해도 그 화면의 단계부터 이어 갑니다.
- "다 됐다"도 규칙입니다(`report_task_status`). 다 된 화면이면 첫 요청에서 바로 끝납니다.

## 앞단 서버가 요청 하나를 처리하는 순서

1. 요청 문장으로 매뉴얼을 고릅니다. **같은 문장일 때만**입니다(띄어쓰기, 대소문자, 끝의 문장부호는 무시하고, 매뉴얼의 `aliases`에 적은 문장도 같은 것으로 봅니다). 비슷한 문장을 짐작해서 고르지 않습니다. 맞는 매뉴얼이 없으면 요청을 그대로 artemis 서버에 넘깁니다.
2. 앱 화면을 아직 읽을 수 없으면(앱이 화면을 그리는 중이라 요소가 0개) 0.6초 기다렸다 다시 보게 합니다. 규칙은 수 ms에 답하므로 앱이 열리는 것보다 빠르기 때문입니다. 다섯 번까지입니다.
3. 지금 화면에 조건이 맞는 규칙을 찾고, 그 대상이 화면에 **하나만** 있으면 바로 답합니다.
4. 없는데 바로 앞 단계를 규칙으로 안내했으면, 한 번만 0.6초 기다렸다 다시 봅니다. 그 단계가 연 화면이 아직 채워지는 중일 수 있기 때문입니다.
5. 그래도 없으면 받은 요청을 artemis 서버에 넘기고 그 답을 그대로 돌려줍니다. 바로 앞 단계를 매뉴얼이 안내했으면 그 동작을(`replay.previous`), 그리고 이 세션에서 매뉴얼로 안내한 단계들을 글로(`event_detail`) artemis에 알려 줍니다.

틀린 안내를 내지 않기 위해 지키는 것입니다.

- 검증된 매뉴얼(`status: verified`)만 씁니다.
- 방금 안내한 규칙이 다음 화면에서도 또 맞으면(눌렀는데 화면이 그대로면) artemis에 묻습니다.
- 한 세션에서 같은 규칙은 두 번까지만 안내합니다.
- 규칙으로 안내했는데 사용자가 막혔다고 하거나 앱이 대상을 찾지 못하면, 그 세션에서는 그 규칙을 다시 쓰지 않습니다.
- 규칙을 찾다가 오류가 나면 결과가 없는 것으로 보고 artemis에 묻습니다.
- 앞단 서버는 사용자의 세션에서 아무것도 등록하지 않습니다. 규칙은 저작 서버만 만듭니다.

응답의 `meta.source`가 `manual`(규칙), `model`(artemis), `wait`(기다림) 가운데 무엇이 답했는지 알려 줍니다.

## 저작 서버가 매뉴얼 하나를 만드는 순서

기기(에뮬레이터)에 해봄 앱이 깔려 있고 접근성 서비스가 켜져 있어야 합니다.

1. 기기의 앱이 저작 서버를 안내 서버로 보게 합니다(`adb reverse`, 앱의 `DEBUG_CONFIG`). 끝나면 원래 주소로 돌려놓습니다.
2. 시작 상태를 만듭니다.
   - `cold`: 최근 쓴 앱을 모두 끄고 홈 화면에서
   - `warm`: 홈 화면에서, 앱은 쓰던 자리 그대로
   - `done`: 이미 다 된 화면에서
3. 사람 역할 스크립트(`manual/human.py`)가 화면의 안내를 따라 누릅니다. 안내는 저작 서버가 답합니다. 맞는 규칙이 있으면 규칙으로, 없으면 artemis 서버로 넘깁니다. 누르는 것은 이 스크립트이고 앱이 아닙니다. 앱은 여기서도 안내만 합니다.
4. 끝까지 갔으면, artemis가 답한 단계 가운데 사람 역할이 해낸 것을 검토해 규칙으로 등록합니다. 잘못 들어갔다 나온 구간은 빼고, 이 화면을 앞의 화면들과 구별할 조건을 만들지 못한 단계는 등록하지 않습니다(그 화면은 계속 artemis가 답합니다). 끝까지 가지 못한 실행에서는 아무것도 등록하지 않습니다.
5. 규칙으로 안내했는데 막힌 단계는 그 규칙을 지웁니다.
6. 같은 시작 상태에서 다시 돌립니다. **모델을 한 번도 부르지 않고 끝까지 가면** 그 시작 상태는 통과입니다.
7. 모든 시작 상태가 통과하면 매뉴얼을 `verified`로 바꿉니다. 앞단 서버는 그때부터 이 매뉴얼을 씁니다.

## 띄우기

파이썬 3.12와 `adb`만 있으면 됩니다. 외부 라이브러리는 쓰지 않습니다. artemis 서버(`haebom-artemis`)가 8765에 떠 있어야 합니다. 기기는 `device/`의 Cuttlefish가 기본입니다(`cd device && ./up.sh`, adb는 `127.0.0.1:6520`).

```bash
# 앞단 서버 (http://127.0.0.1:8770)
python manual/front.py
# 또는
docker compose up -d --build

# 앱이 앞단 서버를 보게 하기 (haebom-app 폴더에서)
python -I scripts/setup_device.py --serial 127.0.0.1:6520 --guide http://127.0.0.1:8770
adb -s 127.0.0.1:6520 reverse tcp:8770 tcp:8770 && adb -s 127.0.0.1:6520 reverse tcp:8766 tcp:8766
```

매뉴얼 저작은 명령 한 줄입니다.

```bash
python manual/author.py run "설정에서 블루투스 화면 열어줘" --id bluetooth
```

서버로 띄워 두고 요청으로 시킬 수도 있습니다.

```bash
python manual/author.py serve                                   # http://127.0.0.1:8780
curl -X POST http://127.0.0.1:8780/author -H "Content-Type: application/json" \
     -d '{"task": "설정에서 블루투스 화면 열어줘", "id": "bluetooth"}'    # {"job": "1121-110533", "status": "running"}
curl http://127.0.0.1:8780/author/1121-110533                    # 진행 기록과 결과
```

Windows에서 한글이 깨지면 `python -X utf8 …`로 실행합니다.

| 요청 | 무엇 | 어느 서버 |
|---|---|---|
| `GET /health` | 상태와 매뉴얼 목록 | 둘 다 |
| `POST /v1/guide/next` | 앱의 안내 요청 | 둘 다 |
| `GET /manuals`, `GET /manuals/<id>` | 매뉴얼 목록과 내용 | 둘 다 |
| `GET /sessions` | 최근 세션마다 규칙이 답한 횟수, artemis가 답한 횟수, 걸린 시간 | 둘 다 |
| `GET /v1/usage` | artemis 서버의 사용량을 그대로 전함 | 둘 다 |
| `POST /author` | 저작 시작. `task`, `id`, `serial`, `starts`, `rounds`, `fresh` | 저작 |
| `GET /author`, `GET /author/<job>` | 저작 작업 목록, 진행 기록과 결과 | 저작 |
| `DELETE /manuals/<id>/steps` | 그 매뉴얼의 규칙을 지우고 초안으로 | 저작 |

| 환경 변수 | 뜻 | 기본값 |
|---|---|---|
| `ARTEMIS_URL` | 넘길 artemis 서버 | `http://127.0.0.1:8765` |
| `MANUALS_DIR` | 매뉴얼 폴더 | `manuals/` |
| `FRONT_HOST`, `FRONT_PORT` | 앞단 서버 | `127.0.0.1`, `8770` |
| `AUTHOR_HOST`, `AUTHOR_PORT` | 저작 서버 | `127.0.0.1`, `8780` |
| `DEVICE_SERIAL` | 저작에 쓸 기기 | `127.0.0.1:6520` (`device/`의 Cuttlefish) |
| `APP_APK` | 기기에 앱이 없을 때 설치할 APK | 없음 |
| `RUNS_DIR`, `RECORD_DIR` | 저작 기록, 앞단 서버의 세션 기록 | `runs/`, 기록 안 함 |

## 확인한 결과

2026-11-21. baseline artemis 서버와 baseline TTS 서버를 같은 컴퓨터에 띄웠고, 사람 역할은 `manual/human.py`입니다.

### 저작

기기 둘에서 저작했습니다. "첫 실행"은 규칙이 없을 때 artemis만으로 간 것이고, 그 아래는 규칙이 모인 뒤 모델을 한 번도 부르지 않고 끝까지 간 검증 실행입니다. 칸의 숫자는 걸린 시간과 (규칙이 답한 횟수 / artemis가 답한 횟수)입니다.

| 매뉴얼 | 기기 | 첫 실행 | `cold` | `warm` | `done` |
|---|---|---|---|---|---|
| 블루투스 화면 열기 | Pixel 에뮬레이터 (Android 16) | 153.1초 (0 / 7) | 22.6초 (5 / 0) | 9.7초 (2 / 0) | 3.9초 (1 / 0) |
| battery 검색 | Pixel 에뮬레이터 | 100.8초 (0 / 7) | 21.0초 (4 / 0) | 12.3초 (2 / 0) | 4.0초 (1 / 0) |
| 블루투스 화면 열기 | Cuttlefish (Android 17 AOSP, Docker) | 99.1초 (3 / 5) | 22.8초 (5 / 0) | 21.3초 (5 / 0) | 3.5초 (1 / 0) |

- [`manuals/bluetooth.json`](manuals/bluetooth.json)에는 Pixel의 규칙 5개와 Cuttlefish의 규칙 2개가 같이 들어 있습니다. Cuttlefish의 첫 실행에서 규칙이 3번 답한 것은 Pixel에서 만든 설정 앱 규칙이 Cuttlefish의 설정 화면에서도 맞았기 때문이고, 새로 등록된 2개는 이 기기의 홈 화면과 알림창에서의 단계입니다.
- [`manuals/battery-search.json`](manuals/battery-search.json)은 규칙 7개이고 그 가운데 하나가 글자 입력입니다. 첫 실행이 설정 앱이 블루투스 화면에 남아 있던 상태에서 시작해서, 그 화면들에서 뒤로 나오는 규칙 셋도 같이 등록됐습니다.
- 블루투스 매뉴얼은 한 번 다시 저작했습니다. 처음 저작에서는 artemis가 "앱 목록을 열어 설정 누르기"로 갔고 그 길이 규칙이 됐는데, 홈 화면에 설정 아이콘이 있으므로 한 단계 긴 길이었습니다. `--fresh`로 다시 저작해 지금의 다섯 단계가 됐습니다.

저작 서버를 만들면서 고친 것입니다.

- `cold`가 홈 화면 앱까지 꺼서 시작 화면이 비어 있었습니다(홈 앱을 묻는 명령이 틀렸습니다). 지금은 홈 앱을 끄지 않고, 최근 쓴 앱을 모두 끕니다.
- 규칙이 앱보다 빨리 답해서, 아직 그려지지 않은 화면을 모델에 묻고 있었습니다. 지금은 읽을 수 없는 화면과, 규칙으로 안내한 직후에 맞는 규칙이 없는 화면에서 잠깐 기다립니다.
- artemis로 넘길 때 앞 단계가 한 단계만 전해져 마지막 판단이 달라지는 일이 있었습니다. 지금은 매뉴얼로 안내한 단계들을 글로 같이 넘깁니다.

### 앞단 서버를 거쳐 앱으로

앱은 고치지 않았고 안내 서버 주소만 바꿨습니다. 기기는 Pixel 에뮬레이터, 앞단 서버는 Docker입니다.

| 요청 | 시작할 때의 상태 | 규칙 / artemis / 기다림 | 걸린 시간 |
|---|---|---|---|
| 블루투스 화면 열기 | 설정 앱을 끄고 | 5 / 0 / 1 | 24.9초 |
| 블루투스 화면 열기 | 블루투스를 꺼 둠 | 4 / 1 / 0. 마지막 화면은 완료 규칙이 맞지 않아 artemis가 판단(7.0초) | 26.2초 |
| 블루투스 화면 열기 | 설정 앱이 검색 화면에 남아 있음 | 5 / 2 / 2. 매뉴얼에 없는 검색 화면에서 돌아오는 두 단계를 artemis가 안내(14.4초, 8.5초)하고 그 뒤는 다시 규칙 | 50.4초 |
| battery 검색 | 매뉴얼을 만들기 전 | 0 / 7 / 0. 전부 artemis로 넘어가 완료 | 87.3초 |
| battery 검색 | 매뉴얼을 만든 뒤, 설정 앱을 끄고 | 4 / 0 / 0~1 | 17.4초, 19.7초 (두 번) |

- 규칙이 답할 때 서버에서 걸리는 시간은 1~30ms입니다.
- 같은 블루투스 요청을 artemis 서버만으로 따라 했을 때는 84.0초였습니다(같은 날, haebom-app의 확인).
- 앞단 서버는 새로 저작된 매뉴얼을 다시 띄우지 않고 읽어 씁니다.
- 둘째, 셋째 줄은 다시 저작하기 전의 블루투스 매뉴얼로 잰 것입니다.
- 에뮬레이터의 내비게이션 바를 제스처 방식에서 버튼 세 개로 바꾼 뒤에도 두 매뉴얼은 그대로 통과했습니다(첫째 줄의 24.9초와 마지막 줄의 19.7초). 규칙에 좌표가 없기 때문입니다.

### 기록된 에뮬레이터 상태로 (벤치마크)

`haebom-artemis`의 벤치마크는 실제 실행 때의 화면을 차례로 서버에 내밀고 답을 채점합니다. 앞단 서버도 같은 요청을 받으므로 주소만 바꿔 그대로 잴 수 있습니다. 저작한 두 요청과 문장이 같은 워크로드 셋(18단계)입니다.

```bash
# haebom-artemis 폴더에서
python bench/run.py bench/workloads/bluetooth.jsonl bench/workloads/bluetooth-again.jsonl bench/workloads/settings-search.jsonl \
    --url http://127.0.0.1:8770 --label manual-front
```

| | 정답 | 단계 지연 중앙값 | 세션당 | 모델 호출 | 비용 |
|---|---|---|---|---|---|
| baseline artemis 서버 | 15 / 15 | 9812ms | 65.7초 | 18 | 0.108 unit |
| 앞단 서버 (매뉴얼 먼저) | 14 / 15 | 34ms | 28.2초 | 6 | 0.024 unit |

- 18단계 가운데 12단계를 모델 없이 답했습니다. 규약 위반과 오류는 0입니다.
- 달랐던 한 단계는 battery 검색의 마지막 단계입니다. 기록된 화면에는 완료 규칙이 맞지 않아 artemis가 판단하는데, "완료" 대신 "검색 누르기"를 골랐습니다. 이 워크로드만 두 번 더 쟀을 때는 두 번 다 5 / 5였습니다. artemis 자신의 기억(스크린샷과 요약)이 없는 상태에서 하는 판단이라 실행마다 갈립니다.
- 다시 저작하기 전의 블루투스 매뉴얼로는 12 / 15였습니다. 두 워크로드의 첫 단계에서 기록은 "설정 누르기"인데 매뉴얼은 "위로 밀기"(앱 목록으로 가는 긴 길)를 냈기 때문입니다.

### 오프라인 재생과 테스트

- 저작과 확인에서 남은 세션의 화면을 규칙 엔진에 다시 넣어 봅니다(`python manual/replay.py runs/*/sessions/*.jsonl runs/front/*.jsonl`). 한 세션에서 배운 규칙을 다른 세션의 화면에 넣어, 그때 사람 역할이 한 동작과 같은지 봅니다. 세션 27개, 1845번 가운데 다른 동작이 나온 것은 68번이고, 전부 홈 화면에서 "설정 누르기"와 "위로 밀어 앱 목록 열기"가 엇갈린 것입니다. 둘 다 설정 앱으로 가는 길이고, 다시 저작하기 전과 후의 세션이 섞여 있어서 생깁니다. 그 밖의 다른 동작은 0번입니다. 못 찾은 화면은 artemis로 넘어가는 화면입니다.
- `python -m unittest discover -s manual/tests`, 56개 통과. 폰도 서버도 모델도 필요 없습니다.

## 에뮬레이터

저작에는 실제로 돌아가는 Android가 필요합니다. `adb`로 닿는 기기면 무엇이든 됩니다.

- 이 컴퓨터에 뜬 Android 에뮬레이터(Pixel, Google Play 이미지): 위의 결과는 이것으로 냈습니다.
- 컨테이너 안의 Cuttlefish(AOSP): [`device/`](device/)에 띄우는 방법이 있습니다. `cd device && ./up.sh` 뒤 `adb connect 127.0.0.1:6520`입니다. 저작 서버를 다른 컴퓨터나 클라우드 VM에 따로 둘 때 씁니다.

Cuttlefish에서 확인한 것입니다(2026-11-21, Windows 11의 Docker Desktop, Android 17 AOSP, 한국어, 1080×2400, 버튼 세 개짜리 내비게이션 바).

- 해봄 앱이 설치되고, adb로 접근성 서비스가 켜지고, 앱이 두 서버에 닿습니다(`adb reverse`가 네트워크로 붙은 adb에서도 됩니다).
- 앱의 첫 화면, 고리, 말풍선, 방향 화살표, ✓·✕ 버튼, 기다림 말풍선이 제대로 그려집니다. 안내 문장은 TTS 서버에서 받아 재생합니다.
- "설정에서 블루투스 화면 열어줘"가 끝까지 갔습니다(93.3초). 설정 앱에 들어오기까지 네 단계는 artemis가 답했고, 그 뒤 세 단계는 Pixel 에뮬레이터에서 저작한 규칙이 Cuttlefish의 설정 화면에서도 그대로 맞아 규칙이 답했습니다.
- 사람 역할 스크립트의 "위로 밀기"는 이 기기의 런처(AOSP Launcher3)에서 앱 목록을 열지 못했습니다. 손으로 민 것과 같은 동작을 adb로 넣었을 때의 문제이고, 앱의 안내는 맞게 떴습니다. artemis는 알림창의 블루투스 타일을 길게 누르는 다른 길로 안내했습니다.
- 기기를 여러 번 껐다 켜는 동안 접근성 서비스 설정이 한 번 풀렸습니다. 저작 서버는 시작할 때 서비스가 꺼져 있으면 다시 켭니다.
- 이 기기에서 저작도 돌렸습니다(`python manual/author.py run … --serial 127.0.0.1:6520`). 결과는 위 표의 셋째 줄입니다.
- 기기는 켜질 때 한국 폰처럼 맞춰집니다: 한국어, 한국 시간, 오전/오후 시계, 버튼 세 개짜리 바, 잠금 화면 없음(`device/entrypoint.sh`). 이 값들은 기기의 데이터(Docker 볼륨)에 남으므로 한 번 맞추면 다시 켜도 그대로입니다. 한글 키보드는 없습니다(AOSP 기본 키보드는 영어 자판뿐입니다).

규칙은 저작한 기기의 화면에서 만든 것입니다. 기종이나 언어가 달라 화면이 다르면 조건이 맞지 않고, 그 화면은 artemis로 넘어갑니다. 느려질 뿐 틀린 안내가 나가지는 않습니다. 화면이 같은 부분(위의 설정 앱)은 다른 기기의 규칙이 그대로 쓰입니다. 그 기기에서 저작을 한 번 더 돌리면 그 기기의 규칙이 같은 매뉴얼에 더해집니다.

기기의 내비게이션 바는 명령으로 바꿉니다. 버튼 세 개: `adb shell cmd overlay enable-exclusive --category com.android.internal.systemui.navbar.threebutton`. 에뮬레이터를 제스처 방식에서 버튼 세 개로 바꾼 뒤에도 두 매뉴얼은 그대로 통과했습니다(24.9초, 19.7초). 규칙에 좌표가 없기 때문입니다.

## 알려진 한계

- 요청 문장이 매뉴얼의 문장과 같아야 합니다. "블루투스 켜는 데 좀 열어줘"처럼 뜻이 같은 다른 문장은 artemis로 갑니다. 문장을 매뉴얼에 이어 주는 일(모델에 한 번 묻기, 목록에서 고르기, QR)은 아직 없습니다.
- artemis는 자기가 답한 단계만 기억합니다. 매뉴얼이 안내한 단계는 넘길 때 바로 앞 단계를 동작으로(`replay.previous`), 그 앞의 단계들을 글로(`event_detail`) 알려 줍니다. 스크린샷과 요약이 딸린 artemis 자신의 기억만큼 자세하지는 않습니다.
- 화면을 구별하는 요소는 정해진 규칙으로 고릅니다(위에서부터 짧고 고정된 글자, 그다음 id). 날짜나 날씨처럼 바뀌는 글자가 조건에 들어가면 그 규칙은 나중에 맞지 않게 되고, 그때는 artemis로 넘어갑니다.
- 완료 규칙에는 화면의 스위치 상태가 들어갑니다. 블루투스가 꺼진 폰에서는 완료 규칙이 맞지 않아 마지막 판단을 artemis가 합니다(위 결과의 둘째 줄).
- 저작 중 한 번, 앱이 시작은 받았는데 안내 요청을 보내지 않은 실행이 있었습니다. 원인은 찾지 못했습니다. 저작 서버는 30초 안에 요청이 없으면 그 실행을 다시 시작합니다.
- 저작은 기기 하나에서 한 번에 하나만 돕니다.
